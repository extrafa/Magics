# Feature Workflow

Пошаговый процесс с обязательными точками ревью пользователя. Не пропускай
этапы и не объединяй их, даже если кажется, что можно быстрее — весь смысл
процесса в том, что пользователь проверяет результат на каждой стадии,
прежде чем двигаться дальше. Это касается и новой фичи с нуля, и ревью/правки
уже существующей — процесс один и тот же в обоих случаях.

Файл CLAUDE.md в корне проекта содержит общие правила стиля и то, как
отличать файлы пользователя от твоих правок (см. конвенцию ///) — эти
правила действуют параллельно с этим процессом, отдельно их не повторяй.

## Этап 0 — Сбор требований

Задай уточняющие вопросы по задаче: что именно нужно (реализовать с нуля,
доработать, поправить, проревьюить существующее), какие есть ограничения,
затрагивает ли это существующие экраны/модели/API, есть ли референсы дизайна.
Не переходи к следующему этапу, пока не наберётся достаточно контекста.

## Этап 1 — Формулировка задачи

Напиши чёткую формулировку задачи (task spec): что делаем — будь то новая
фича, ревью существующей, багфикс или доработка — зачем, какой результат
считается готовым (acceptance criteria). Покажи пользователю.

**Стоп.** Пользователь читает и правит/дописывает формулировку и, при
необходимости, детали реализации. Жди его правок или явного "ок, погнали"
перед следующим этапом.

## Этап 2 — План реализации

Изучи существующий проект / конкретную фичу, которую ревьюишь или дорабатываешь
(структуру, связанные файлы, паттерны, которые уже используются). Составь
план, разбитый на маленькие чанки — каждый чанк должен быть самостоятельной,
проверяемой единицей работы (не "переписать весь модуль", а "добавить модель X",
"починить баг в Y", "поправить логику Z"). Пронумеруй чанки по порядку.

Сохрани план файлом в docs/plans/ (создай папку, если её нет), с именем вида
YYYY-MM-DD-короткое-название-plan.md (дата — сегодняшняя). Не показывай план
только в чате — он должен существовать как файл, чтобы пользователь мог
оставлять правки прямо в нём. НЕ добавляй файлы из docs/plans/ в Xcode target
(target membership) — они не должны попадать в билд приложения.

**Стоп.** Пользователь открывает файл сам и оставляет правки строками с ///
прямо под нужными пунктами плана (см. конвенцию /// в CLAUDE.md). Когда
пользователь говорит "прочитай план и обнови по правкам" — прочитай файл,
учти все строки с ///, обнови план, удали те /// строки, которые уже учёл,
сохрани файл заново и коротко перечисли, что изменил. Повторяй, пока
пользователь явно не одобрит план (в файле не останется /// комментариев,
либо пользователь явно скажет "план ок").

## Перед началом реализации — создание ветки

После одобрения плана, перед первым чанком (если ещё не в фича-ветке):
создай ветку от develop командой вида git checkout -b feature/<короткое-название>
(или fix/<короткое-название> для багфикса). Возьми короткое название из
task spec, отдельно не спрашивай пользователя про имя ветки. Ветку создаёт
Клод через git в терминале — пользователю не нужно ничего создавать вручную
через GitKraken или иначе.

## Этап 3 — Реализация по чанкам

Для каждого чанка из одобренного плана, по одному за раз:

1. Реализуй только этот чанк, ничего сверх него.
2. Покажи диф / список изменений.
3. **Стоп.** Пользователь проходит по изменениям, оставляет комментарии.
4. Доработай по комментариям, покажи снова — повторяй, пока пользователь не
   одобрит именно этот чанк.
5. Только после одобрения переходи к следующему чанку.

Не забегай вперёд и не реализуй следующий чанк "заодно, чтобы не терять
контекст" — это ломает процесс проверки.

Это относится и к маленьким задачам. Если задача настолько мала, что план не
сохраняется отдельным файлом и всё укладывается в один чанк (см. правило
"маленькие шаги" в CLAUDE.md) — диф всё равно показывается, и пользователь
всё равно должен одобрить его, прежде чем переходить дальше (к Этапу 4 или
куда угодно). "Один чанк, без файла плана" не означает "без ревью и без
стопа" — эти два допущения независимы, пропуск файла плана НИКОГДА не
означает пропуск диффа и одобрения.

## Этап 4 — Проверка сборки

После того как все чанки одобрены — просто собери проект (build), убедись,
что нет ошибок компиляции. НЕ запускай приложение и не пытайся сам проверять,
что фича реально работает (в симуляторе, руками и т.д.) — это тратит кредиты
почти без пользы, потому что пользователь всё равно тестирует всё сам на
устройстве/симуляторе дотошно. Твоя задача на этом этапе — только убедиться,
что код компилируется. Если сборка падает — почини и сообщи, что было не так.

## Этап 5 — Pull Request и полный дифф-ревью

Работаем по Git Flow: фича-ветки создаются от develop и мержатся обратно в
develop, а не в main. В main идут только релизы (из release-веток), это
отдельный процесс, не связанный с этим скиллом.

По просьбе пользователя ("создай PR", "смерж-реквест") — создай Pull/Merge
Request между текущей фича-веткой и develop. Покажи ссылку на PR.
Пользователь пройдётся по всему дифу целиком и оставит комментарии — дорабатывай
по ним так же, как в этапе 3.

Когда пользователь просит смержить PR — используй squash-merge с явно заданным
коротким сообщением коммита (те же правила, что в разделе "Коммиты" в
CLAUDE.md: английский, без префиксов, одна строка). НЕ используй дефолтное
поведение gh pr merge, которое склеивает заголовок PR и список всех коммитов
фичи в одну простыню без переноса строки — это даёт нечитаемую историю.
Пример: gh pr merge --squash --subject "Fix empty catch blocks in StoreManager" --body "".

## Этап 6 — Финальная перепроверка

По команде "перепроверь всё в соответствии с планом реализации" — сверь
итоговый результат с планом из Этапа 2 пункт за пунктом: ничего не
пропущено, ничего лишнего не добавлено, acceptance criteria из Этапа 1
выполнены. Эта проверка должна выполняться на максимальном эффорте:
напомни пользователю запустить /effort ultracode перед этим этапом, если
он ещё не включён.

После того как пользователь подтвердит, что PR смержен в develop —
перемести файл плана из docs/plans/ в docs/plans/archive/ (создай папку,
если её нет), оставив имя файла без изменений. Это держит docs/plans/
чистым — там видны только планы фич, которые ещё в работе.

---

Важно: каждый "Стоп" в этом файле — обязательная точка, где инициатива
переходит к пользователю. Не додумывай одобрение и не продолжай молча.
