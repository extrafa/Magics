# results.first у NWBrowser — случайный peer вместо нужного — план

Task spec: ревью uamoder. `browseResultsChangedHandler` отдаёт `Set<NWBrowser.Result>`
— у `Set` нет порядка, `.first` (`PhantomDrawSessionManager.swift`, `startBrowsing`)
возвращает произвольный элемент, зависящий от хеширования. Сразу после этого
браузер отменяется и обнуляется, переключиться на другого peer уже нельзя.
Сценарий: рядом два человека показывают этот же трюк (или второй тестовый
sender на столе) — магик молча подключается не к своему зрителю. Заметить
это из UI невозможно: `peerName` вычисляется и кладётся в
`.connected(peerName:)`, но нигде не отображается — в `PhantomDrawReceiverView`
статичный бейдж «Connected» без имени.

## Решение (оба пункта из (в) ревью)

1. **Минимум** — показывать имя peer в бейдже receiver-а вместо статичного
   «Connected», чтобы несовпадение было видно.
2. **Правильно** — sender публикует код спаривания в TXT-записи Bonjour-сервиса
   (`NWListener.Service(txtRecord:)`), receiver фильтрует `results` по
   совпадению кода вместо слепого `.first` — подключается только к
   реальному своему peer, а не к произвольному элементу `Set`.

TXT-запись передаётся в открытом виде по mDNS, но это не ослабляет защиту:
код и так двузначный и не является секретом сам по себе (реальная защита —
PSK на TLS), это только устраняет случайный выбор из `Set`.

## Чанк 1 — PhantomDrawReceiverView.swift: имя peer в бейдже

`connectionBadge` читает `peerName` из `viewModel.session.connectionState`
(кейс `.connected(peerName:)`) и показывает его вместо статичного текста
«Connected» (если состояние почему-то не `.connected` — fallback на
«Connected», такого на практике не бывает, бейдж рендерится только пока
подключено).

## Чанк 2 — PhantomDrawSessionManager.swift: sender публикует код

`startListening(code:)`: `NWListener.Service` получает `txtRecord:` с кодом
(`NWTXTRecord`, один ключ, именованная константа вместо строкового литерала
россыпью).

## Чанк 3 — PhantomDrawSessionManager.swift: receiver фильтрует по коду

`startBrowsing(code:)`: `results.first` → `results.first(where:)` с проверкой
TXT-записи результата на совпадение с `code`. Если совпадения ещё нет —
не подключаемся, ждём следующего обновления `browseResultsChangedHandler`
(браузер остаётся активным, как и раньше при пустом `results`).

## Чанк 4 — сборка + живая проверка

Happy path (обычное подключение sender/receiver) — код должен доходить до
TXT-записи и совпадать, подключение должно проходить как раньше, в бейдже
receiver-а должно появиться реальное имя устройства sender-а. Сценарий с
несколькими одновременными sender-ами рядом детерминированно не
воспроизвести без второго физического устройства-приманки — логику фильтра
проверю чтением кода.

## Итог: чанки 2-3 откачены

Живая проверка на двух симуляторах показала регресс: `results.first(where:)`
никогда не находил совпадение по коду — `NWBrowser.Result.metadata` (TXT-запись)
не успевает/не доходит стабильно, особенно в связке симулятор-симулятор, из-за
чего подключение зависало в `.searching` навсегда — хуже, чем баг из ревью
(редкий шанс подключиться не к тому peer). Чанки 2 и 3 (TXT-запись кода +
фильтр браузера) откачены; в релиз идёт только чанк 1 — имя peer в бейдже
receiver-а. Это закрывает «минимум» из пункта (в) ревью (несовпадение видно
глазами), «правильное» решение (фильтр по коду) признано слишком ненадёжным
для этой кодовой базы и не реализовывалось.
