# Небезопасный пейринг в PhantomDraw — план

Task spec: найдено ревью uamoder. `NWParameters.tcp` — без TLS, трафик в
открытом виде. `newConnectionHandler` принимает ЛЮБОЕ входящее соединение без
проверки. Кто угодно в той же Wi-Fi-сети, знающий тип сервиса
`_phantomdraw._tcp`, может подключиться к sender (телефону зрителя) и
перехватить сессию — рисовать вместо зрителя, подглядывать за рисунком или
подсунуть магу поддельные штрихи.

Решение: короткий одноразовый числовой код в качестве TLS pre-shared key —
обсуждено и подтверждено в чате. Обоснование: это единственный из
рассмотренных вариантов, который даёт настоящее шифрование + взаимную
аутентификацию, а не просто визуальную проверку (numeric-comparison) или
общий пароль без реальной аутентификации (захардкоженный passcode).
Единственный ручной шаг (ввод 2-значного кода) происходит целиком на этапе
сетапа, пока оба телефона ещё у мага — до того, как зритель вообще увидит
экран, так что иллюзия трюка не страдает.

Важная поправка после проверки: `NWParameters(passcode:)` **не существует**
в Network.framework — такого инициализатора нет. Реальный способ — вручную
собрать `NWProtocolTLS.Options()` и добавить PSK через
`Security.sec_protocol_options_add_pre_shared_key(_:_:_:)`, передав код и
identity как `DispatchData`. Прогнан и проверен рабочий прототип на Mac
(подписанный бинарник с сетевыми entitlements, TCP по loopback):
совпадающие ключи → хендшейк проходит и данные передаются; разные ключи →
сервер валит соединение с `-9846: bad MAC` (криптографическая проверка
реально происходит, не для вида); короткий 2-значный код работает без
дополнительного растягивания/хеширования. Неожиданность: явный вызов
`sec_protocol_options_set_min_tls_protocol_version(_, .TLSv13)` ломает
хендшейк (generic internal error) — без него TLS 1.3 всё равно
согласовывается сам, раз PSK задан; в коде это не проставляем и оставляем
комментарий о причине, чтобы не "починили" обратно.

Порядок пейринга: телефон зрителя (sender) первым генерирует код и начинает
слушать с ним, встроенным в свои `NWParameters`. Телефон мага (receiver)
получает этот код, маг его вводит, и только после этого начинается поиск с
такими же `NWParameters`. Неверный код просто проваливает TLS-хендшейк — это
попадает в уже существующую ветку `.failed` → "Could Not Connect" / "Try
Again", новую обработку ошибок писать не нужно.

## Чанк 1 — PhantomDrawModels.swift + PhantomDrawSessionManager.swift (проброс passcode)

- `PhantomDrawConnectionState`: добавить `.enteringCode` — состояние receiver
  после выбора роли, до того как код введён и поиск запущен.
- `PhantomDrawSessionManager`:
  - `@Published private(set) var pairingCode: String?`
  - `makeParams(code:)` — строит `NWProtocolTLS.Options()`, добавляет PSK
    через `sec_protocol_options_add_pre_shared_key` (код → key, фиксированная
    строка-идентификатор приложения → identity), оборачивает в
    `NWParameters(tls:tcp:)`, `includePeerToPeer = true` остаётся. Без
    `set_min_tls_protocol_version` (см. поправку выше).
  - `startAsSender()` — генерирует случайный 2-значный код, публикует его в
    `pairingCode`, передаёт в `makeParams(code:)` для listener'а.
  - `startAsReceiver(code:)` — принимает код, который ввёл маг;
    `connectionState = .searching` выставляется только после того, как код
    известен; используется в `makeParams(code:)` для browser/connection.

## Чанк 2 — PhantomDrawViewModel.swift

- `selectRole(.receiver)` больше не стартует сессию сразу — выставляет
  `connectionState = .enteringCode` и ждёт.
- Новый `submitReceiverCode(_ code: String)` → `session.startAsReceiver(code: code)`.
- `selectRole(.sender)` не меняется по сигнатуре — `session.startAsSender()`
  сам генерирует код внутри.

## Чанк 3 — PhantomDrawView.swift (UI)

- Ветка sender в `searchingView`: показать `viewModel.session.pairingCode`
  крупно, с подписью в духе "покажи это магу".
- Receiver: новый экран для `.enteringCode` — короткое числовое поле ввода +
  кнопка продолжить, вызывающая `viewModel.submitReceiverCode(...)`.
- Неверный код: отдельно ничего не чиним — провал TLS-хендшейка уже идёт
  через существующее состояние `.failed`.

## Out of scope

- QR/NFC-пейринг — приятнее по ощущениям ("волшебный" UX, без ввода), но
  существенно больше объём (разрешение на камеру, экран сканирования).
  Отдельная задача, если понадобится позже.
- Rate-limiting повторных неудачных попыток подключения — Network.framework
  не даёт хука на "код неверный N раз подряд"; полагаемся на короткое время
  жизни кода (одна сессия трюка) и на то, что 2-значного пространства
  достаточно для этой модели угроз — цена компрометации здесь "кто-то
  подглядел за учебным рисунком", а не что-то чувствительное. Если
  приложение станет достаточно популярным, чтобы в одном помещении могли
  запуститься два независимых сеанса и коды совпали, можно поднять до
  3 знаков без изменения архитектуры.
